# SRM 企业级 Agent 应用 · 需求对齐文档

> 状态：**已确认**（v1.0）— 四项关键决策已拍板，进入 M1 实施
> 原则：基于 v1 RAG 项目（`srm-maxkb`）升级，**新建独立仓库 `srm-agent`，不改动原仓库**
> 本文目标：先对齐架构与标准，再动手写代码

## 0. 已确认决策（v1.0）

| 决策点 | 结论 | 连带影响 |
|---|---|---|
| 技术栈基座 | **Python / FastAPI 延续** | v1 检索层可迁移；Agent 生态（LangGraph / MCP / RAGAS）Python 优先 |
| 编排实现 | **LangGraph** | 采用 StateGraph + 检查点；需自己补齐护栏与工具治理抽象（LangGraph 不替你做治理） |
| 业务边界 | **含完整写操作** | **HITL 审批、幂等键、审计留痕必须在 M1 就落地**，不能后置 |
| 交付节奏 | **分阶段，M1 优先** | M1 = 仓库 + 状态图 + 工具中心 + 只读/写工具 + 治理三件套，验收后再叠加观测与记忆 |

> **重要提醒**：选 LangGraph 只解决了"编排"，**没有解决"治理"**。工具级授权、幂等、
> 审批门、审计、成本计量仍需自建抽象层——这也是本项目的工程价值所在，不能指望框架自带。

## 1. 项目定位

| 项 | v1（现有 `srm-maxkb`） | v2（新建 `srm-agent`） |
|---|---|---|
| 范式 | 单趟 RAG 管线 | **有状态的 Agent 运行时** |
| 能力 | 只读问答 | 问答 + **业务查询/办理**（工具调用） |
| 编排 | 硬编码 if/else | **显式状态图 + 迭代护栏** |
| 适用 | 单租户演示 | **多租户 / 生产可治理** |
| 卖点 | 检索做得深 | **工程完备度**（治理/观测/评测/成本） |

一句话定位：**面向供应商的企业级 Agent 平台**——不只是"能答"，而是"能办事、可审计、可回滚、成本可控"。

## 5. Agent 编排与工具调用

### 5.1 编排：显式状态图（推荐）而非自由 ReAct 循环

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| 自由 ReAct 循环 | 灵活 | 不可控、难测、难观测、易失控 | ✗ |
| **显式状态图** | 可控、可测、可观测、可插护栏 | 需预先设计节点 | ✓ **推荐** |
| 计划-执行 DAG | 适合确定性流程 | 缺乏动态反思 | 部分吸收 |

**五节点流程**：`Router → Planner → Executor → Reflector → Responder`
- `Reflector` 判定信息不足 → 回环 `Planner` 重规划（**受迭代上限约束**）
- 每节点职责单一，均产出可观测 span

### 5.2 迭代护栏（企业级必备，防止 Agent 失控）

| 护栏 | 阈值建议 | 超限行为 |
|---|---|---|
| 步数上限 | `max_steps = 6` | 强制进入 Responder 并标注"未完全解决" |
| Token 预算 | 单请求 8k / 会话 32k | 触发摘要压缩，再超则降级小模型 |
| 墙钟超时 | 30s | 中断并返回已得结果 |
| 工具失败重试 | 指数退避 ×2 | 转入降级链，仍失败则 RAG-only 兜底 |
| 循环检测 | 相同工具+参数重复 3 次 | 强制跳出 |

### 5.3 工具契约

每个工具必须声明（这是治理的基础）：

```python
class Tool(Protocol):
    name: str                    # 唯一标识
    description: str             # 给 LLM 看的语义描述（决定调用准确率）
    args_schema: type[BaseModel] # Pydantic → 自动导出 JSON Schema
    required_scopes: set[str]    # 调用所需权限（工具级授权）
    side_effect: bool            # 是否有副作用（写操作）
    idempotent: bool             # 是否幂等
    timeout_ms: int              # 超时
    retry_policy: RetryPolicy    # 重试策略
```

要点：
- **只读 / 写操作分离**：`side_effect=True` 的工具默认进入审批门
- **幂等键**：写工具必须支持 `idempotency_key`，防重复提交
- **并行执行**：`Executor` 对无依赖的工具并发调用
- **结构化输出**：LLM 返回严格经 Pydantic 校验，失败则带错误信息重试一次，再失败降级——**绝不裸解析自由文本**

## 6. 记忆与状态管理

| 层级 | 内容 | 载体 | 生命周期 |
|---|---|---|---|
| **工作记忆** | 当前轮的计划、工具结果、草稿 | AgentState（内存 + 检查点） | 单轮 |
| **会话记忆** | 多轮对话历史 | PostgreSQL | 会话级，超 token 预算自动摘要压缩 |
| **长期画像** | 供应商身份、角色、偏好、历史问题 | PostgreSQL（需显式同意） | 持久 + TTL，可删除 |
| **情节记忆** | 历史交互摘要，可检索 | pgvector | 持久 |
| **语义记忆** | 知识库（业务蓝图） | pgvector | 版本化 |

关键设计：
- **状态检查点**：AgentState 可序列化落库 → 支持断点续跑、长任务、失败重试
- **租户隔离**：所有记忆以 `(tenant_id, user_id)` 为键，检索层强制注入过滤条件
- **合规**：入存储前 PII 脱敏；支持删除权（个保法 / GDPR）；留存期可配
- **轨迹回放**：从 trace 重建 state，用于线上问题复现

## 7. 可观测性

分层目标：**从"知道慢"到"知道哪一步慢、为什么错"**。

| 能力 | 方案 | 关键指标 |
|---|---|---|
| 链路追踪 | OpenTelemetry，一次请求 = 一棵 span 树 | 每节点/每次工具调用/每次 LLM 调用的耗时与状态 |
| 指标 | Prometheus | p50/p95/p99 延迟、工具成功率、降级率、护栏拦截率、token/成本 |
| 日志 | 结构化 + 关联 ID（trace_id / request_id / session_id） | 全链路可串联 |
| LLM 观测 | prompt/response 落库（**PII 脱敏后**） | 单次成本、按租户归集、异常 prompt 回溯 |
| 评测 | 黄金集 + 回归门禁 | 指标下滑即阻断合并 |
| 告警 | — | 错误率、p99、成本突增、护栏拦截激增 |

**评测体系升级**（v1 只有 20 题准确率，不够）：
- 检索：Recall@k、MRR、NDCG
- 生成：faithfulness（是否忠于原文）、answer relevance
- Agent：**工具选择准确率、参数正确率、任务完成率、步数效率**
- 对抗集：Prompt 注入、越权访问、幻觉诱导

## 8. 安全与权限

| 项 | 方案 |
|---|---|
| 认证 | JWT（用户）+ API Key（服务）+ 预留 OIDC/SSO |
| 授权 | RBAC 打底，**ABAC 补充**（属性：租户、供应商等级、数据范围） |
| **工具级授权** | 权限校验下沉到工具：`required_scopes`，不同角色可见工具集不同 |
| **数据级隔离** | 检索层强制注入 `tenant_id` / 可见范围过滤（**补 v1 P0 缺口**） |
| Prompt 注入防护 | 检索内容是**不可信输入**：指令层级隔离 + 分隔符 + 注入检测 + 输出约束 |
| PII 脱敏 | 入库/入日志前识别脱敏；不同角色脱敏粒度不同 |
| 输出校验 | 禁止臆造承诺（价格/交期）、禁止泄露系统提示词与其他租户数据 |
| 审计日志 | 谁在何时用何参数调用了何工具——追加写、不可变、可导出 |
| 密钥管理 | **移除硬编码默认密码**；密钥经环境变量/密钥管理注入，启动强校验 |
| 限流配额 | 按租户 + 用户 + 工具维度的速率与配额 |

## 9. 部署与 CI/CD

**部署标准**
- 容器：多阶段构建、非 root 用户、镜像最小化
- K8s：Helm Chart、HPA、就绪/存活探针、优雅停机、ConfigMap/Secret 分离
- 环境：dev → staging → prod 分级晋升，配置与镜像解耦
- 数据迁移：Alembic 版本化，可回滚
- 发布策略：金丝雀 / 蓝绿；**模型、Prompt、知识库索引均需可独立回滚**

**CI 流水线（PR 触发）**
```
lint(ruff) → type(mypy) → unit test → integration test
  → eval 回归门禁（指标下滑 > 阈值即阻断）
  → 构建镜像 → 安全扫描(Trivy/CodeQL) → 依赖审计
  → 推送制品 → CD 部署（staging 自动 / prod 手动审批）
```

**CD**：GitHub Actions + 环境审批；或 ArgoCD GitOps（声明式、可审计）。

## 10. 我补充的企业级要素（你未提及但必须考虑）

> 这些是"能跑的 Demo"与"敢上生产"的分水岭，也是面试时体现深度的地方。

| # | 要素 | 为什么必须有 |
|---|---|---|
| 1 | **LLM 成本治理（FinOps）** | 模型分层路由（简单问题走小模型）、语义缓存、按租户成本归因、预算熔断。企业最先追问的就是"一个月烧多少钱" |

| 6 | **确定性测试** | LLM mock + 工具 mock，让 Agent 测试可复现。否则 CI 里全是 flaky test |
| 7 | **ADR 架构决策记录** | 记录"为什么选状态图不选 ReAct"这类决策。企业协作与面试讲述的核心材料 |

| 9 | **数据合规与留存** | 供应商是外部方，数据边界敏感。留存期、删除权、审计导出、跨境/出境合规 |
| 10 | **MCP 协议支持** | 工具生态标准化，避免自研工具锁死，也是当前行业热点 |
| 11 | **可解释性与用户信任** | 不止引用来源，还要展示"Agent 做了什么"（执行轨迹），同时不泄露系统提示词 |
| 12 | **灾备与降级链** | LLM 主→备→兜底；工具熔断；整体降级为 RAG-only 也要能答 |

## 11. 决策记录（已拍板，见第 0 节）

四项决策已确认：**Python / LangGraph / 含完整写操作 / 分阶段 M1 优先**。

选 LangGraph 后需要明确的取舍：

| 项 | LangGraph 提供 | 本项目需自建 |
|---|---|---|
| 编排 | StateGraph、条件边、检查点、interrupt | — |
| 护栏 | 仅 `recursion_limit` | 步数 / token / 墙钟预算、循环检测、降级链 |
| 工具治理 | 无 | 工具级授权、幂等键、审批门、审计、超时重试 |
| 观测 | 需接 LangSmith 或自埋 | OpenTelemetry span 树、成本归因 |
| 评测 | 无 | 黄金集、对抗集、CI 回归门禁 |

结论：**LangGraph 降低编排成本，治理成本不变**。M1 的核心工作量在右侧自建部分。
