# ADR 0002：写操作的审批与幂等设计

- 状态：**已接受**
- 日期：2026-08-30
- 关联：ADR 0001

## 背景

业务边界确定为**含完整写操作**。写操作与只读操作的本质区别是：**失败或重试会产生不可逆的副作用**。
典型生产事故：

1. 用户重复点击 → 重复建单
2. 网络超时重试 → 重复扣款/重复提交
3. Agent 自主执行写操作 → 未经授权的业务变更

## 决策

### 1. 所有 `side_effect=True` 的工具必须经过审批门

工具的 `side_effect` 声明与 `requires_approval` 强绑定（后者是前者的派生属性），
**不允许开发者单独关闭**——避免"某个工具忘了配审批"这类人为疏漏。

审批决策三级优先级：

1. 持有 `approval:auto` scope → 策略自动放行（内部可信账号）
2. LangGraph `interrupt` 可用 → 挂起等待人工，恢复时记录审批人
3. 以上都不满足（无 interrupt 能力且非可信账号）→ **拒绝**

第 3 条是关键：**fail-closed**。拿不到明确的人工决策时默认拒绝，
而不是默认放行 —— 宁可让用户多等一次审批，也不能擅自改数据。
不存在「外部审批系统回调预设」这一独立分支：无 interrupt 能力时无法可靠挂起，
此时直接 fail-closed 比「放行」更安全。

### 2. 写操作必须携带幂等键，否则拒绝执行

```python
if not ctx.idempotency_key:
    raise ToolError("写操作必须携带 idempotency_key，否则无法保证幂等")
```

幂等键由编排层生成：`md5(tenant_id + user_id + tool + args)`，
保证相同租户/用户下相同操作得到相同 key，**跨租户不会碰撞**。

命中幂等键时**回放首次结果**（含首次生成的工单号），而非重新执行。

### 3. 审计留痕覆盖完整链路

`approval_requested` →（`human_decision` / `auto_approved`）→ `tool_execute_approved` / `tool_rejected`

每个条目含：时间、租户、用户、会话、工具、参数、决策、幂等键。追加写、不可变。

### 4. 非幂等工具不重试

`Executor` 的重试逻辑检查 `spec.idempotent`，非幂等工具失败后不重试 ——
对非幂等写操作重试可能造成重复副作用，这是**比重试成功率更重要**的约束。

## 理由

- **审批门**解决"谁批准了这个变更"（问责）
- **幂等键**解决"重试会不会重复执行"（正确性）
- **审计**解决"事后能不能追溯"（合规）
- 三者缺一，写操作就不具备上生产的前提

## 影响

- 写操作至少多一次往返（挂起 → 审批 → 恢复），延迟上升。这是**刻意接受**的代价。
- `MemorySaver` 仅适用于单进程；多副本部署必须用 `AsyncPostgresSaver`，
  否则审批恢复可能落到另一个进程上找不到状态（M4 处理）。
- 生产环境 `_IDEMPOTENCY_STORE` 需替换为 Redis（`SET key value NX EX 86400`），
  当前内存实现仅保证单进程幂等。
